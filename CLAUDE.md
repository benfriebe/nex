# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build Commands

```bash
# Build libghostty (required once, or after ghostty submodule changes)
# The lib/ directory is gitignored -- you must build it locally.
cd ghostty && zig build -Dapp-runtime=none -Doptimize=ReleaseFast -Demit-macos-app=false && cd ..
mkdir -p lib
cp $(find ghostty ghostty/.zig-cache -path "*/macos-*/libghostty.a" -type f | head -1) lib/libghostty.a

# Generate Xcode project (required after changing project.yml)
xcodegen generate --spec project.yml

# Build (also serves as typecheck — there is no separate typecheck step)
xcodebuild -scheme Nex -destination 'platform=macOS' -skipMacroValidation build

# Run all tests (the `Nex` scheme's testTargets wiring routes the run
# into the `NexTests` target — there is no standalone `NexTests` scheme)
xcodebuild -scheme Nex -destination 'platform=macOS' -skipMacroValidation test

# Run a single test class or method
xcodebuild -scheme Nex -destination 'platform=macOS' -skipMacroValidation \
  -only-testing:NexTests/PaneLayoutTests test
xcodebuild -scheme Nex -destination 'platform=macOS' -skipMacroValidation \
  -only-testing:NexTests/PaneLayoutTests/testSplitHorizontal test

# Lint & format
swiftlint lint                # lint check
swiftlint lint --fix          # auto-fix lint issues
swiftformat .                 # format code
swiftformat --lint .          # format check (no write)

# Run all checks (format-check → lint → build → test)
make check
```

`-skipMacroValidation` is required because TCA uses Swift macros.

## Architecture

**SwiftUI + TCA (Composable Architecture)** app targeting macOS 14+, Swift 6.

### Reducer hierarchy
- `AppReducer` — top-level state: workspace list, repo registry, socket messages (agent lifecycle + pane/workspace commands), git status, external indicators (menu bar/dock badge)
- `WorkspaceFeature` — per-workspace: panes, layout tree, focus, splits, agent status. Connected via `.forEach(\.workspaces, action: \.workspaces)`
- `SettingsFeature` — user preferences (worktree base path, appearance, keybindings)

### Terminal rendering — libghostty
- `GhosttyApp` — singleton wrapping `ghostty_app_t`. Initializes the runtime, dispatches action callbacks (title changes, pwd changes, close, desktop notifications) via `NotificationCenter`.
- `GhosttyConfig` / `GhosttyConfigClient` — reads user's `~/.config/ghostty/config`
- `SurfaceView` — `NSView` subclass hosting a `ghostty_surface_t`. Handles keyboard/mouse input, text input protocol, Metal rendering.
- `SurfaceManager` — singleton owning all `SurfaceView` instances by pane UUID. Thread-safe via `NSLock`. Surfaces persist across workspace switches (removed from view hierarchy but kept alive so PTY processes continue).

### Pane layout
- `PaneLayout` — recursive enum (`leaf(UUID)` | `split(direction, ratio, first, second)` | `empty`). Handles splitting, removing, moving panes, frame computation, and divider positioning.
- `PredefinedLayout` — enum of five tmux-style layouts (even-horizontal, even-vertical, main-horizontal, main-vertical, tiled). `buildLayout(for: [UUID])` generates the tree; first UUID is the "main" pane. Cycled via `⌘⇧Space` or `nex layout cycle`.
- `Pane` — model with id, working directory, git branch, agent status, Claude session ID.
- `PaneGridView` / `SurfaceContainerView` — SwiftUI views that render the layout tree and embed `SurfaceView` via `NSViewRepresentable`.

### Markdown panes
- **Entry points**: ⌘O (file picker filtered to `.md`), drag-and-drop a `.md` file onto the window, Finder **Open With → Nex** (or double-click when Nex is the default `.md` handler), or the `nex md [--here] <file>` / `nex open <file>` CLI commands. ⌘O and drag-drop route through `AppReducer.openFileAtPath`; the CLI `open`/`md` wire command routes through `AppReducer.openFile`. All converge on `WorkspaceFeature.openMarkdownFile`. The GUI entry points stay markdown-only; the CLI `nex open` routes a URL/hostname to a web pane and otherwise routes a local file by extension (see the CLI section), while `nex md` always opens a markdown pane.
- **Finder "Open With" (issue #197)**: `Info.plist` declares markdown via `CFBundleDocumentTypes` (role Editor, `LSHandlerRank` `Alternate` — appears in *Open With* and settable as default, without hijacking an existing default handler) + `UTImportedTypeDeclarations` importing `net.daringfireball.markdown` (extensions `md`/`markdown`). `NexAppDelegate.application(_:open:)` forwards each opened markdown file URL to `FileOpenGate` (an `@MainActor` AppKit→store bridge mirroring `QuitGate`), which `NexApp.onAppear` wires to `.openFileAtPath` — the same path as drag-drop. Two-stage cold-launch queue: `FileOpenGate` buffers files that arrive before `.onAppear` wires the store; `AppReducer.State.pendingFileOpens` parks files that arrive before the async state load sets `activeWorkspaceID`, drained by `.flushPendingFileOpens` from `.stateLoaded` (transient — not persisted).
- **View mode** (`MarkdownPaneView`): `WKWebView` with `drawsBackground=false`. File content is parsed via swift-markdown → `MarkdownHTMLRenderer` → full HTML document with CSS (light/dark). Live file watching via `DispatchSource` detects writes, renames, and deletes (vim-style save). Scroll position is preserved across reloads.
- **Code-block copy button**: `MarkdownHTMLRenderer` wraps every fenced code block in a container with a hover-revealed `.code-copy-btn`, and `MarkdownCodeCopyScript` (injected into the preview) posts the raw code text through the `copyCodeBlock` WKWebView script-message handler, which writes it to `NSPasteboard.general`. The button flashes a checkmark via a `.copied` class for 1.5s and swaps its `aria-label` to "Copied" for assistive tech. A re-entry guard ignores repeat clicks during the copied window.
- **Front-matter**: if a file begins with a `---`-fenced YAML block, `FrontMatterExtractor` pulls it out before swift-markdown parsing and `FrontMatterRenderer` emits a styled two-column table at the top of the preview. Parsing uses Yams; malformed YAML falls back to a styled raw block, and blocks larger than 64 KiB are skipped (rendered as plain markdown) to guard against pathological input.
- **Edit mode** (`MarkdownEditorView`): `NSTextView` (plain text, monospace 13pt) in an `NSScrollView`. Auto-saves to disk with 500ms debounce.
- **Toggle**: ⌘E switches between view and edit mode (only when a markdown pane is focused). Header button also toggles.
- **Background**: both views receive `ghosttyConfig.backgroundColor` / `backgroundOpacity` so they match terminal panes. The pane container also has a matching background fill for any gaps.
- **Git branch**: detected at open time via `gitService.getCurrentBranch` on the file's parent directory.

### Diff panes
- **Entry points**: `nex diff [<path>]` from the CLI, the bindable `open_diff` action (default unbound), or the "plusminus" button next to a repo association in the workspace inspector. All route through `AppReducer.openDiffPath` → `WorkspaceFeature.openDiffPane`.
- **Renderer** (`DiffHTMLRenderer`): pure-Swift line-by-line classifier — emits `<div class="line line-{add|del|hunk|context|file-header}">` with GitHub-style colors and the same dark-mode detection as `MarkdownHTMLRenderer`. Each `diff --git` opens a `<details class="file" open>` block with a sticky `<summary>` (the file path); clicking the summary toggles collapse, and `position: sticky` keeps the current file's header pinned while scrolling through its hunks. Empty diff → "No changes" placeholder.
- **View** (`DiffPaneView`): `WKWebView` mirroring `MarkdownPaneView` minus edit mode and file watching. Refreshes when the pane regains focus and when the header refresh button (`arrow.clockwise`) bumps a per-pane `refreshToken` tracked in `PaneGridView`.
- **Inputs**: `pane.workingDirectory` is the repo path; `pane.filePath` is the optional file/dir scope passed to `git diff -- <path>`. No `--staged` / ref-range support yet.
- **Git invocation**: new `gitService.getDiff(repoPath:targetPath:)` shells out via the existing `runGit` helper. Errors render as a placeholder line in the pane.

### Pipeline panes (issue #282 — v1 + round 3: fan-out edges, canvas UX)
- **Scope**: the agent-orchestration-pipelines design — a graph of agent nodes with outcome-conditional edges, run by an engine that spawns panes, types launch commands, and routes on an explicit `nex pipeline done|fail|partial` handoff. All seven build phases have landed: shared model, native canvas editor, run/node-run models + persistence, pure routing/templating logic, `nex pipeline` socket + CLI verbs, live execution (spawn/readiness/bounce-back/liveness), and the monitor UI + StatusBar surfacing + recovery. **Round 3** added fan-out (multiple edges off the same `(from, outcome)`, run concurrently) plus four canvas/discoverability UX fixes — see the "Round 3" bullets interleaved below.
- **Fan-out (round 3)**: duplicate `(from, on)` edge pairs are legal — only an exactly identical `(from, on, to)` triple is rejected. When a node hands off, EVERY matching edge fires: each either parks a pending approval, coalesces into an already-active NodeRun for the same target (no double-spawn — the traversal still counts), or spawns a fresh NodeRun/pane. There is no AND-join/barrier semantics in v1 — a node with two inbound edges just gets re-engaged twice, independently, whichever fires first (future work). `{{feedback}}` binds to the specific NodeRun whose handoff spawned the recipient (`PipelineNodeRun.feedbackSourceNodeRunID`), not "whichever else in the run most recently finished" (ambiguous once branches run concurrently). A branch that fails with no matching fail edge (or trips `maxTraversals`) fails the WHOLE run and marks every other still-active NodeRun `.interrupted` (panes left open). The run completes once there are no active NodeRuns and no pending approvals AND at least one branch reached `.done`; if every branch dead-ends without one ever reaching `.done`, the run is `.failed` instead of hanging forever. `PipelineRun.currentNodeRunID` is retired — replaced by the computed `activeNodeRunIDs`/`blockingNodeRunIDs`/`mostRecentNodeRun` (`PipelineRun.swift`); `nex pipeline approve|deny` gained `--edge <key>` to disambiguate when more than one gate is pending (required unless there's exactly one).
- **Model** (`Nex/Models/PipelineDefinition.swift`): `PipelineDefinition` (nodes, edges, inputs, `ui.nodes` position map) with `validate()` (unknown refs, duplicate ids/edges, empty prompts, `agent: codex` rejected in v1, `headless` + `permissionMode: plan` rejected, unreachable nodes as warnings) and a Yams-backed YAML codec (`fromYAML`/`toYAML`). The definition's `id` (filename slug) is deliberately excluded from the YAML payload — `PipelineDefinitionStore` assigns it from the filename.
- **Storage** (`Nex/Services/PipelineDefinitionStore.swift`): CRUD + `watch()` over `~/.config/nex/pipelines/*.yaml` (config-file-as-source-of-truth, the `ProfilesSettingsView` idiom), with self-write echo suppression so autosave doesn't trigger its own reload.
- **Pane** (`PaneType.pipeline`): sidecar `WorkspaceFeature.State.pipelinePanes: [UUID: PipelinePaneState]` (mirrors `webPanes`) holds the open document, canvas selection, undo/redo stacks, zoom/pan, and `mode: .edit | .monitor(runID:)`; only the `pipelineName` is persisted (`pane.pipelineName`, migration `v19_pipeline_pane`) — the document itself reloads from YAML on restart via `AppReducer`'s `.stateLoaded` handler, and `mode` always starts `.edit` (a monitor view re-attaches once the pane's document and the run's live state are both loaded).
- **Editor** (`Nex/Features/PipelinePane/`): native SwiftUI canvas (no WKWebView) — `PipelineCanvasView` (drag-to-reposition nodes, double-click to add, tap to select, a floating "+ New Node" corner toolbar button pinned to the viewport — round 3 — as the discoverable counterpart to double-click), `PipelineEdgeLayer` (bezier + arrowhead `Canvas` rendering, curves bent per `PipelineUIMetadata.edges` overrides), `PipelineInspectorView` (trailing panel editing node/edge fields), `PipelineLibraryView` (list/new/delete). `PipelineAutoLayout` computes a deterministic layered layout (BFS depth from `entry`) for nodes missing a saved position; `PipelineCanvasGeometry` is the pure hit-testing/transform layer, now also owning the edge-curve bezier math (`edgeControlPoints`/`cubicBezierPoint`/`edgeHandlePosition`/`updatedEdgeOffset`) shared between rendering, hit-testing, and the round-3 drag-to-bend handle. Edits go through `WorkspaceFeature.Action.pipelineEdit(paneID:edit:)` (a `PipelineEdit` enum), autosave through the store on a 500ms debounce, with a capped (50) undo/redo stack.
- **Edge curve handles (round 3)**: each edge gets a small draggable dot at its curve midpoint (`PipelineCanvasView.edgeHandle`, live in both edit and monitor mode — a pure layout change, same precedent as node position drags); dragging bends the curve via `PipelineEdit.moveEdgeHandle(edgeKey:offset:)`, which writes a `PipelineEdgeUI(offset:)` into `document.ui.edges[edgeKey]` keyed by `PipelineEdge.identityKey` (`"<from>|<on>|<to>"` — needed once duplicate `(from,on)` pairs are legal). A zero/absent offset reproduces the original deterministic curve, so hand-authored YAML never needs a `ui.edges` block. Hit-testing (`PipelineCanvasGeometry.hitTest`) samples the actual bent bezier, not the straight chord, so tap-to-select still finds a heavily-bent edge.
- **Node card status (round 3)**: `PipelineCanvasGeometry.nodeSize` grew (64pt → 92pt tall) so the full status word (e.g. "awaitingApproval") never clips, and `PipelineNodeView` gained a state-coloured SF Symbol badge in the card's top-right corner (`play.circle.fill` running, `checkmark.circle.fill` done, `xmark.circle.fill` failed/timedOut, `exclamationmark.triangle.fill` stalled, `pause.circle.fill` awaitingHuman, `circle.dotted` spawning, `questionmark.circle.fill` interrupted) alongside the existing text row.
- **Monitor UI** (`Nex/Features/PipelinePane/PipelineRunHUD.swift`, `RunPipelineSheet.swift`, `PipelinePaneView.swift`): the pane-header play button opens `RunPipelineSheet` (one field per declared input, skipped when the definition has none) and dispatches `AppReducer.Action.pipelineRunFromPane(paneID:inputs:)`, which flips the pane to `.monitor(runID:)` on success. In monitor mode the edit header is replaced by `PipelineRunHUD` (run name, status, elapsed, done/total node tally, Cancel/Resume/Back-to-Edit as the run's status allows, plus one Approve/Deny row PER pending gate — round 3, fan-out can leave more than one branch awaiting approval at once, each targeted by its `edgeKey`) and `PipelineCanvasView` renders per-node status overlays via `PipelineNodeView`'s `run: PipelineNodeRunDisplay?` (pending nodes dimmed, every currently-ACTIVE branch's card gets the accent glow — round 3, was a single `currentNodeRunID`-driven glow — done/failed get a colored dot, `×N` attempt chip past the first attempt); `PipelineNodeView` is `Equatable` (`nonisolated static func ==`, required for a `View: Equatable` conformance under Swift 6 strict concurrency) comparing only render-affecting fields so a status tick re-renders one node, not the canvas. Structural edits (add-node double-click/toolbar, the inspector) are hidden/disabled in monitor mode; position drags (nodes and edge handles) still work. Double-click a node card → `onJumpToNode` → `AppReducer.Action.pipelineJumpToNode(paneID:nodeID:)` resolves that node's latest `PipelineNodeRun.paneID`, switches workspace, and focuses it.
- **Known simplifications** (v1 editor, follow-up work): edges are added via inspector affordances rather than drag-from-port; no rubber-band multi-select; no `⌘Z`-style keyboard layer (toolbar Undo/Redo buttons instead); a node's slug can't be renamed once created (only its display name); no AND-join/barrier semantics for a multi-inbound-edge node (round 3 fan-out); a stall/pause still applies at the whole-run level even though only one branch may be stuck (round 3 fan-out follow-up).
- **Sidebar entry point (round 3)**: the sidebar's bottom action bar (next to "+ New Workspace") gained an `arrow.triangle.branch` icon button — `WorkspaceListView` — opening the pipeline pane on the active workspace, since the prior entry points (chevron menu, command palette, unbound keybinding) were too hidden per user feedback.
- **Entry point**: the default-unbound `open_pipeline` keybinding (`NexCommands` → `WorkspaceFeature.Action.openPipelinePane`), opening a `.pipeline` pane on the library view.
- **Run model** (`Nex/Models/PipelineRun.swift`): `PipelineRun` (id, definitionID, frozen `definitionSnapshot`, `status: PipelineRunStatus` + free-text `statusDetail`, location, workspaceID with no FK so it survives workspace deletion, runDir, inputs, `nodeRuns: IdentifiedArrayOf<PipelineNodeRun>`, `edgeTraversals: [String: Int]` keyed by `PipelineEdge.identityKey` (`"<from>|<on>|<to>"` — round 3, was `"<from>|<on>"` before fan-out made `to` part of an edge's identity)) and `PipelineNodeRun` (id, nodeID, attempt, paneID?, agentSessionID?, `status: PipelineNodeRunStatus`, summary, outputPath, warnings, `feedbackSourceNodeRunID: UUID?` — round 3, the NodeRun whose handoff spawned this one, migration `v21_pipeline_fanout`). `PipelineRun.pruned(_:keepingTerminal:)` keeps the most recent 50 terminal runs; non-terminal runs are never pruned. `activeNodeRunIDs`/`blockingNodeRunIDs`/`mostRecentNodeRun`/`pendingApprovals` (round 3) are computed, not persisted — there is no single "current node" pointer anymore. `statusDetail` carries two parseable-prefix conventions rather than new DB columns: `PipelineRunPauseReason` (`[stalled_node]` / `[app_restart]` / `[pane_closed]`, `PipelineRun.swift`) for why a run is `.paused`, and `PipelinePendingApproval` (`[approval to=<node> edge=<key> from=<node-run-id>]`, `PipelinesFeature.swift`, one token PER pending gate — round 3) for the routing target(s) while `.awaitingApproval` — both free-text-with-a-scannable-prefix, matching the "statusDetail is free text" DB design.
- **Engine — pure logic** (`Nex/Services/PipelineEngine.swift`): `PipelineEngineLogic` (directly unit-testable, no DI) — `renderPrompt` (hand-rolled `{{dotted.path}}` templating over `inputs.*`/`nodes.<id>.output`/`nodes.<id>.summary`/`run.id`/`run.dir`/`feedback`, unresolved placeholders render empty + warn, always appends a "Pipeline context" section + the mandatory handoff appendix), `evaluateTransition` (fan-out — round 3 — fires EVERY edge matching `(from, outcome)` at once, returning `PipelineTransition.routes([PipelineRoute])`; declared-only per-edge `maxTraversals` loop guard fails the whole handoff atomically if any fired edge would exceed it; partial→done fallback applies to the whole matching set), `composeLaunchCommand` (PTY-injection-safe: validated `model` charset, single-quoted+escaped `env` values, control characters rejected outright) and `composeResumeCommand` (the bounce-back `claude --resume <id>` variant — same env-prefix convention, session id validated via `AgentKind.isSafeSessionID`), `prepareAttemptDir`/`writePrompt`/`writeResultJSON` (file work under `~/Library/Application Support/Nex/pipeline-runs/<runID>/`). Wrapped in a `PipelineEngine` struct-of-closures `DependencyKey` (GraftService style) so `PipelinesFeature` tests can fake routing.
- **Engine — live execution** (`Nex/AppReducer+PipelineEngine.swift`): owns everything that touches `surfaceManager`/`state.workspaces`, since `PipelinesFeature.State` alone can't spawn panes.
  - **Spawn decision** (`pipelineEngageNode`): a node is a *bounce* only if this run already has a prior `PipelineNodeRun` for the same node id with a bound pane — first-ever visits are always a fresh spawn. Bounce liveness reads straight off the pane's own `agentSessionID` (no separate debounce bookkeeping): if it still matches the prior attempt's tracked session, the session is live (`pipelineBounceLiveSession` — just a file-pointer message, no relaunch); if it's nil (cleared by `WorkspaceFeature`'s existing SessionEnd match-guard, issue #178) but a session id was captured, resume it (`pipelineBounceResume` — types `claude --resume <id>` with the same `NEX_PIPELINE_*` env-prefix convention so `$NEX_PIPELINE_ATTEMPT` is still readable post-resume); otherwise fresh-spawn into a new pane.
  - **Fresh spawn** (`pipelineSpawnFresh`): mints a paneID, labels it `pipe:<nodeID>:<run-id-prefix-8>`, dispatches `WorkspaceFeature.Action.splitPane`/`.createPane` (empty workspace) with that pre-minted id — the same pattern `handlePaneCreate`/`handlePaneSplit` use for CLI-visible pane ids.
  - **Readiness gate** (`pipelineTypeCommandAfterSurfaceReady` + the `PipelinesFeature.Action.Delegate` cases `nodeCommandTyped`/`readinessTimedOut`/`spawnFailed`): polls `surfaceManager.surface(for:)` (iteration-counted, not wall-clock `ContinuousClock.now`, so the whole wait routes through the injected `clock` dependency and resolves instantly under `ImmediateClock`/`TestClock`), then a shell-readiness grace, then types the command and starts a 30s cancellable SessionStart timeout (`PipelineReadinessTimeoutID`). One retry (retype + re-arm) before the node fails synthetically. A synthetic failure (`pipelineFailNodeSynthetically`) routes exactly like an explicit `nex pipeline fail` — same `applyHandoff` call.
  - **Handoff → next node**: `PipelinesFeature.applyHandoff` (still pure, `PipelinesFeature.State`-only) now appends the next node's `PipelineNodeRun` itself on a non-approval `.route` and reports its id back via `HandoffResult.applied(_, spawnNodeRunID:)`; `pipelineFollowUpOnHandoff` (`AppReducer+PipelineEngine.swift`) is what actually calls `pipelineEngageNode` for it — the split keeps `applyHandoff` directly `TestStore`-testable while the pane-touching follow-up stays app-level.
  - **Liveness rules**, all in `AppReducer+PipelineEngine.swift`, hooked from the raw wire-event cases in `AppReducer+Socket.swift`'s `socketReducer` (not the generic `.workspaces(.element(_, action:))` interceptors, since `.notification` also proxies through `.agentStopped` for pane-status bookkeeping and would be indistinguishable there from a real Stop): `pipelineHandleStop` arms a 120s cancellable grace timer (`PipelineStopGraceTimeoutID`, `cancelInFlight: true`) on a zero-background-task Stop, cancels it if background work is still in flight; `pipelineHandleNotification` cancels the grace timer and flags the node `.awaitingHuman` (suspends the timeout rather than arming it); `pipelineHandleAgentStarted` clears `.awaitingHuman` on the next turn; `pipelineHandleSessionStarted` rebinds `agentSessionID` and either completes the readiness gate (`.spawning` → `.running`, delivers a queued pointer message from `state.pipelinePendingPointerMessages`) or clears a `.stalled` node (a late SessionStart un-stalling); `pipelineHandleSessionEnded` stalls the node ONLY if the ending session id still matches what the NodeRun is tracking — the same match-guard idiom as `WorkspaceFeature`'s own SessionEnd handling, which makes the compaction dual-fire (`SessionEnd(old)` + `SessionStart(new)`, either order) resolve correctly without a separate wall-clock debounce. A late handoff for the stalled node (`applyHandoff`) clears the stall and routes normally. `pipelineHandlePaneClosed` and `cancelPipelineRuns` (workspace delete) pause/cancel per issue section 3's failure-mode table.
  - **Approval / manual control** (`pipelineApprove`/`pipelineDeny`/`pipelineCancel`/`pipelineRetry`/`pipelineResume`, called from both the CLI handlers below and the GUI HUD buttons via `handlePipeline*FromPane`): approve appends + engages the pending target node; deny cancels the run; retry/resume both funnel through `pipelineReengageNode` (force `.running`, fresh attempt of the current node, framed feedback message — resume's is restart-specific: "verify whether you completed the mission").
  - **PTY safety** (non-negotiable, matches issue section 7 pitfall 3): every typed command is built exclusively from `composeLaunchCommand`/`composeResumeCommand`'s validated/quoted output; prompts and feedback travel via files (`pipelineWritePrompt` → `engine.writePrompt`), never typed directly; pointer/feedback messages (`pipelineMissionPointer`) are file-path references only, sent via `paneSendText`, and only ever queued for delivery AFTER a SessionStart confirms a claude TUI actually owns the PTY.
- **Recovery**: on `.stateLoaded`, any node run left non-terminal by an unclean shutdown loads `.interrupted` and its run `.paused` with `PipelineRunPauseReason.appRestart` (set at persistence-load time, `DatabaseService`/`PersistenceService`); panes bound to those NodeRuns are excluded from the blind agent-session auto-resume loop (`AppReducer.swift`'s `.stateLoaded` handler) since the engine — not that loop — owns their lifecycle. `nex pipeline resume` re-engages via the same `pipelineReengageNode` bounce path: since `.stateLoaded` still recreates a surface for every shell pane (just without auto-typing `claude --resume` into pipeline-owned ones), the interrupted node's pane already has a fresh shell waiting, so resume's fresh attempt lands in that same pane via the ordinary bounce-resume/fresh-spawn decision.
- **Persistence**: migration `v20_pipelines` (`DatabaseService.swift`) adds guarded `pipelineRun` (definitionYAML snapshot, status/statusDetail/location/workspaceID/runDir/inputsJSON/edgeTraversalsJSON) and `pipelineNodeRun` (cascades on its parent run) tables; `PipelineRunRecord`/`PipelineNodeRunRecord` ride `PersistenceSnapshot`/`writeRecords`/`load` on the existing 500ms debounce. No schema changes were needed for phases 6-7 — pause reasons and pending-approval targets ride the existing `statusDetail` column (see Run model above). Migration `v21_pipeline_fanout` (round 3) adds a guarded `feedbackSourceNodeRunID` column to `pipelineNodeRun`; `pipelineRun.currentNodeRunID` stays in the schema unused (a stored, empty legacy column) rather than a destructive drop — the model field it backed is gone, replaced by computed properties.
- **Socket + CLI** (`SocketServer.swift`, `AppReducer+PipelineSocket.swift`, `AppReducer+PipelineEngine.swift`, `Tools/nex-cli/nex.swift`'s `handlePipeline`): `pipeline-run` / `pipeline-handoff` / `pipeline-status` / `pipeline-list` / `pipeline-validate` / `pipeline-cancel` / `pipeline-retry` / `pipeline-approve` / `pipeline-deny` / `pipeline-resume` / `pipeline-watch` — all in `replyCommandAllowlist`, all parsed before the mandatory-`paneID` guard (none require `NEX_PANE_ID`). `nex pipeline run <name> [--input k=v]...` validates synchronously (definition loads + `validate()` has no errors + required inputs present + a resolvable workspace for `location: current`) before the reply, which now carries `status: "launching"` — spawning itself happens post-reply via `pipelineLaunchRun`; `location: workspace`/`worktree` mint their own workspace asynchronously the same way (only genuinely async failures — `git worktree add`, spawn — surface post-reply via `pipeline status`/`watch`). `nex pipeline done|fail|partial` resolves the target NodeRun via `NEX_PANE_ID` (finds the run whose NodeRun's `paneID` matches and is `running`/`awaitingHuman`) or via `--run <id> --node <slug> --force` from outside any pane, then calls `PipelinesFeature.applyHandoff` followed by `pipelineFollowUpOnHandoff` (spawns whatever the routing decided). `nex pipeline cancel|retry|approve|deny|resume <run-id>` share `handlePipelineControl` (resolve run, run-status precondition, dispatch to the matching `AppReducer+PipelineEngine` orchestrator, reply `{ok, run_id, status}`); `approve`/`deny` additionally take `--edge <key>` (round 3, `PipelineEdge.identityKey`) — required when fan-out has left more than one gate pending (`pendingApprovalPrecondition` rejects an ambiguous/unmatched request up front with the candidate keys), optional when there's exactly one. `retry`/`resume` re-engage every currently blocking (stalled/interrupted, plus — for `retry` on a `.failed` run — each node's latest failed attempt) NodeRun, not just one, since fan-out can leave more than one branch blocked at once. `nex pipeline watch <run-id>` mirrors `web console --follow` exactly: `AppReducer.State.pipelineWatchSubscribers: [UUID: [UInt64: ReplyHandle]]`, torn down on `socketSubscriberDisconnected` AND when `pipelineFanOutWatch` sees the run reach a terminal state; the CLI uses `sendJSONAndStream` (no read timeout, Ctrl-C closes the FD). `Self.runJSON` (round 3) surfaces `active_node_ids` and, while `.awaitingApproval`, `pending_approvals` at the run level, and each node-run entry gets `from_node_id`/`from_node_run_id` when it has a feedback source — parallel branches are unambiguous in `pipeline status`/`watch` output.
- **GUI monitor entry points** (`AppReducer.Action.pipelineRunFromPane`/`pipelineCancelRunFromPane`/`pipelineApproveRunFromPane`/`pipelineDenyRunFromPane`/`pipelineResumeRunFromPane`/`pipelineBackToEditFromPane`/`pipelineJumpToNode`/`pipelineFocusRun`): every GUI action carries only a `paneID` (or, for the StatusBar, a `runID`) — resolution of the pane's workspace and its monitor-mode `runID` happens inside the handler (`AppReducer+PipelineEngine.swift`), so `PipelinePaneView`/`PaneGridView`/`ContentView` stay plain prop/closure plumbing with no direct store reads (the existing `onPipelineEdit`-style pattern). `handlePipelineRunFromPane` shares `createPipelineRun` (the validate → create → launch core, `AppReducer+PipelineSocket.swift`) with the socket handler so the two entry points can't drift.
- **StatusBar** (`Nex/Features/StatusBar/StatusBarController.swift`, `StatusBarPopoverView.swift`): the menu-bar popover gets a "Pipelines" section above the per-workspace pane list — `StatusBarPipelineItem` (run id, name, status, current node id) computed in `.updateExternalIndicators` from `state.pipelines.runs.filter { !$0.status.isTerminal }`. Clicking a row dispatches `.pipelineFocusRun(runID:)`, which focuses the run's current node's pane (or just switches to its workspace if nothing has spawned yet, e.g. still `.launching`/`.awaitingApproval`).

### Synchronise input (tmux-style)
- **Entry points**: the default-unbound `toggle_sync_input` keybinding, a per-pane header button, and `nex pane sync on|off|toggle|status|exclude|include`. When active, a keystroke in any synced pane is mirrored to every other synced pane in the same workspace.
- **State** (`WorkspaceFeature.State`): `isSyncInputActive: Bool` + `syncInputExcluded: Set<UUID>`. The computed `syncedPaneIDs` is the broadcast group: only `.shell` panes, minus the excluded set, and only when ≥2 qualify (so a lone terminal never "syncs" to itself). `syncInputExcluded` is cleared on every transition of `isSyncInputActive`, so `sync exclude` must run *after* `sync on`.
- **Actions**: `toggleSyncInput`, `setSyncInputActive(Bool)`, `setSyncInputExcluded(paneID:excluded:)`. Every reducer path that mutates `panes` or the sync fields calls `refreshSyncGroup`, which pushes the current `syncedPaneIDs` into `SurfaceManager.setSyncGroup(workspaceID:paneIDs:)`.
- **Broadcast** (`SurfaceManager`): holds `syncGroups: [UUID: Set<UUID>]` (per workspace). `SurfaceView.sendKey` calls `broadcastKey(from:key:)`, which mirrors the libghostty key event to every sibling in the source's group (best-effort; dead surfaces are skipped). `isSyncing(paneID:)` backs the header badge.

### Persistence — GRDB
- `DatabaseService` — manages SQLite via GRDB's `DatabasePool` (prod) or `DatabaseQueue` (tests, in-memory).
- `PersistenceService` — debounced (500ms) full-state serialization. Clears and re-inserts all records on each save. Tables: `WorkspaceRecord`, `PaneRecord`, `RepoRecord`, `RepoAssociationRecord`, `AppStateRecord`.

### Agent monitoring & CLI
- `SocketServer` — Unix domain socket at `/tmp/nex.sock` + optional TCP listener on `127.0.0.1:<port>`. Receives newline-delimited JSON from the `nex` CLI. Messages use `"command"` key. Commands: `start`, `stop`, `error`, `notification`, `session-start`, `session-end`, `pane-split`, `pane-create`, `pane-close`, `pane-name`, `pane-resize`, `pane-send`, `pane-send-key`, `pane-sync`, `pane-sync-exclude`, `pane-move`, `pane-move-adjacent`, `pane-move-to-workspace`, `pane-list`, `pane-capture`, `workspace-list`, `workspace-create`, `workspace-move`, `workspace-delete`, `workspace-profile`, `group-list`, `group-create`, `group-rename`, `group-delete`, `layout-cycle`, `layout-select`, `open`, `diff`, `ping` (plus the `web-*` family for the web pane). Group icon management is deliberately UI-only (context menu); there is no `group-set-icon` wire command.
- **Request/response framing**: most commands are fire-and-forget (server reads, acts, drops the FD). Commands in `replyCommandAllowlist` (currently `workspace-list`, `group-list`, `pane-list`, `pane-close`, `pane-capture`, `pane-send`, `pane-send-key`, `pane-split`, `pane-create`, `pane-name`, `pane-resize`, `pane-move-adjacent`, `pane-sync`, `pane-sync-exclude`, `workspace-create`, `workspace-delete`, the `graft-*` verbs, `ping`, and the `web-*` verbs) return structured JSON — the server allocates a `SocketServer.ReplyHandle`, the reducer writes a single newline-terminated JSON line via `reply.send(...)`, then `reply.close()` cancels the client's dispatch source (EOF on the CLI side). Success payloads are `{"ok":true, ...}`; failures are `{"ok":false,"error":"<message>"}` and the CLI exits non-zero. Reply handlers must gracefully accept `reply: nil` for the legacy fire-and-forget path. (`workspace-profile` is fire-and-forget.)
- **`ping` command**: request/response health check. The reducer's `handlePing` replies with `{"ok":true,"version":"<short>","build":"<build>","pid":<n>}` — used by `nex doctor` to verify the running app can dispatch socket commands round-trip, and as a cheap version probe so the CLI can flag CLI/app drift.
- **TCP transport**: enabled via `tcp-port = <port>` in `~/.config/nex/config`. Binds to `127.0.0.1` only (no auth needed — SSH tunnels handle remote security). Use cases: dev containers connect via `host.docker.internal:<port>`, remote agents connect via SSH reverse tunnel (`ssh -R <port>:localhost:<port> remote`).
- `SocketMessage` — enum representing all wire messages (agent lifecycle + pane commands + workspace + group commands).
- **Name-or-ID resolution** (`State.resolveGroup` / `State.resolveWorkspace`): commands like `workspace-move`, `group-rename`, `group-delete` accept either a UUID string or a case-sensitive name. UUID wins when it matches; names must be unique to resolve (ambiguous → no-op).
- `nex` CLI — standalone Swift CLI in `Tools/nex-cli/`. Compiled as a post-build script and bundled into `Contents/Helpers/`. Subcommand structure:
  - `nex event stop|start|error|notification|session-start|session-end [--agent claude|codex] [--message ...] [--title ...] [--body ...]` — `session-end` (Claude Code SessionEnd hook) clears the pane's tracked `claudeSessionID` when it still matches the ending session, so an exited agent session is not `claude --resume`d on next launch (issue #178)
    - **Codex CLI native status (issue #101)**: Codex CLI ≥ 0.142 has a Claude-style lifecycle hooks system (`~/.codex/hooks.json`, same JSON shape as Claude's `settings.json` `"hooks"` key, payload on stdin with `session_id`). `install-hooks.sh` wires four hooks — `UserPromptSubmit`/`Stop`/`SessionStart` plus `PermissionRequest` → `nex event notification` (Codex has **no** `SessionEnd` or `Notification` event) — each with `--agent codex`. The flag rides the wire as `agent` (absent = claude, unknown → claude via `AgentKind.fromWire`) on `agentStarted`/`sessionStarted` (session_id dual-fires included — an untagged dual-fire would flip the kind back to claude on every codex turn end). `Pane.agentKind` (persisted, `v18_pane_agent_kind`) labels the running badge ("codex · mm:ss") and picks the restart/reopen resume command via `AgentKind.resumeCommand` (`claude --resume X` vs `codex resume X`); it is deliberately NOT cleared by `stateLoaded`'s session-id clearing (last-known display value; the resume tuples capture it first). `pane list --json` exposes it as `agent` (last-known kind, not "attached now"). Known limitations: no codex SessionEnd → a stale codex session id can persist after codex exits (pre-#178 parity: restart may `codex resume` an old session; the pane also sits in the status bar's inactive bucket); post-approval the pane reads "awaiting input" until the next turn signal (Claude parity); codex hooks need one-time trust via `/hooks` inside codex, re-granted whenever hooks.json changes. Codex notification defaults: title "Codex", body from the `PermissionRequest` payload's `tool_name` ("Approval requested: <tool>").
    - **Background-aware status (issues #215, #220)**: on `stop` / `notification`, the CLI reads the hook payload's `background_tasks` array — a live snapshot of `run_in_background` shells + background subagents (`type: "shell"` / `"subagent"`) — and forwards a count as the wire field `background_tasks` (only when > 0, so the common path is wire-identical). `WorkspaceFeature.agentStopped(paneID:backgroundTaskCount:)` keeps the pane `.running` when the count is > 0 instead of flipping to `.waitingForInput`, and the socket reducer suppresses the synthetic "waiting for input" notification + dock bounce for that pane (killing the churn from the repeat Stops that fire as each background unit completes). The pane self-recovers: background work finishing re-invokes Claude → `UserPromptSubmit` → `start` (which resets the count to 0) → the next `Stop` arrives with an empty array. The transient count rides on `Pane.backgroundTaskCount` (not persisted), surfaces in `pane list --json` as `background_tasks` and in the pane header running-badge as "· N running". `background_tasks` is an *observed* Claude Code field, not a documented contract, so the CLI guards defensively — a missing / renamed / misshaped field yields 0 → today's behaviour. (Note: `SocketMessage.agentStopped` / `.notification` and `WorkspaceFeature.Action.agentStopped` gained the `backgroundTaskCount` associated value — a stale call site surfaces as a misleading "unable to type-check" error, so grep all sites when touching these cases.)
  - `nex pane split|create|close|name|send|move|move-to-workspace [options]` — `split`, `create`, and `close` all accept `--target <name-or-uuid>` to address a specific pane; with `--target`, `close` works without `NEX_PANE_ID`. `close` rejects bare positional arguments and unknown options with a usage error — addressing a pane other than the caller always goes through `--target`, so a typo can never silently close the calling pane. The same leftover-arg rejection (shared `rejectLeftoverArgs` helper) now guards `split` / `create` / `capture` / `list` too, so no pane command silently drops a stray positional or unknown flag (issue #237); `--help`/`-h` on any of them prints usage instead of executing. `close` and `send` also accept `--workspace <name-or-id>` to narrow label resolution to a single workspace (disambiguates cross-workspace label collisions)

The CLI no longer calls `requirePaneID()` for them; it includes `pane_id` only when the env var is set (to scope label resolution to the caller's workspace), and routes by `--target` (UUID = global, label needs `NEX_PANE_ID` or `--workspace`).   - `nex pane send-key --target <name-or-uuid> [--workspace <name-or-id>] <key>` — request/response. Delivers a single named keystroke (`enter`, `return`, `tab`, `escape`/`esc`, `space`, `backspace`, `up`, `down`, `left`, `right`, `ctrl-c`) outside any bracketed-paste envelope. Companion to `pane send` for TUI targets that opt into bracketed-paste (Claude Code, vim, etc): `pane send "text"` then `pane send-key enter` is the reliable submit path. Callable from outside a Nex pane (no `NEX_PANE_ID` required) — mirrors `pane close` / `pane capture`; UUID targets work globally, label targets need either `NEX_PANE_ID` or `--workspace`. Unknown key names are rejected with a structured error before the surface is touched. The byte-mapped keys (enter/tab/escape/space/backspace/ctrl-c) go through the libghostty key-event path with `mods=NONE` and `text=<byte>` so the raw byte hits the PTY's line discipline (e.g. ctrl-c → `\x03` → SIGINT); arrow keys leave `text=nil` so libghostty translates the keycode based on terminal mode (DECCKM `\eOA` vs `\e[A`).

  - `nex pane capture [--target <name-or-uuid>] [--workspace <name-or-id>] [--lines N] [--scrollback]` — request/response. Reads another pane's terminal contents and prints them to stdout. Without `--target`, captures the current pane (requires `NEX_PANE_ID`). The target is flag-only: a bare `nex pane capture <uuid>` is rejected with a usage error rather than silently falling back to capturing the caller (issue #237). `--scrollback` extends the read region from the visible viewport to the full screen.   - `nex pane resize [--target <name-or-uuid>] [--workspace <name-or-id>] (--ratio <0..1> | --grow [amt] | --shrink [amt]) [--json]` — request/response (issue #241). Resizes a pane against its *immediate* split sibling by adjusting the enclosing split's ratio, so agents can keep a coordinator prominent or balance a fanned-out grid without the GUI. Reuses `PaneLayout.updatingSplitRatio` (the same method behind the GUI divider drag / the `updateSplitRatio` action, replicating its `currentLayoutIndex = nil` reset): `handlePaneResize` resolves the target (same `resolvePaneTarget` scoping as `pane name` — callable from outside a Nex pane, UUID = global, label needs `NEX_PANE_ID` or `--workspace`), maps it to the enclosing split via `PaneLayout.enclosingSplitPath(of:)`, then translates the requested pane *share* into the split's stored first-child ratio (a second-child pane's share is `1 - ratio`). Bulk: the CLI loops one `workspace-delete` per id (exact-duplicate ids deduped) and exits non-zero if any *delete* failed (a transport/empty/invalid-JSON reply is fatal for the whole batch). **Refuses to delete the last remaining workspace** (mirrors the GUI context-menu `.disabled(store.workspaces.count <= 1)` — deliberately stricter than the ⌘W close-last-pane path, which can reach zero). An *ambiguous* name (matches >1 workspace) is rejected with a distinct "ambiguous" error, since name resolution requires a unique match. **Running-agents guard**: deleting a workspace that still has active agents (panes/parked with status ≠ `.idle`) is refused with `{ok:false, error:"…has N running agent(s); pass --force…", active_agents:N}` unless `--force`/`-y` is given (mirrors the app-quit warning). An *empty* workspace (no panes) has no `path`, so its worktree can't be pruned automatically (a documented limitation — delete before closing the panes to retain the directory, or `git worktree remove` it by hand). `--json` emits a compact per-id result array; each row: `id` (the argument as typed — a name or UUID, echoed back), `ok`, and on success `workspace_id`, `workspace_name`, `path?`, plus `worktree_pruned?` / `worktree_error?` when `--prune-worktree` was given, or `error` (with `active_agents` on a running-agents refusal) on failure.

  - `nex group rename <name-or-id> <new-name>`
  - `nex group delete <name-or-id> [--cascade]` — without `--cascade`, children promote to top level
  - `nex group reorder <name-or-id> --order <id1,id2,...> [--json]` (issue #225) — request/response; rewrites the group's `childOrder` (the actual sidebar render order, which `workspace move --index` could not reorder within a group) to the given member sequence. `--order` accepts comma- or space-separated tokens, each a member UUID or a name unique within the group; a non-member token or a duplicate is an error (nothing is written). Members omitted from `--order` keep their relative order at the tail. `handleGroupReorder` mutates `state.groups[id:].childOrder` and emits `.persistState`; renders live. Reply: `{ok, group_id, group_name, order}` (full member UUIDs)
  - `nex group sort <name-or-id> --by name|last-activity|last-accessed [--desc] [--json]` (issue #225) — request/response; the same `handleGroupReorder` path, computing `childOrder` by a key instead of an explicit list. `name` = case-insensitive workspace name; `last-activity` = most recent pane activity in the workspace; `last-accessed` (alias `last-modified`) = `workspace.lastAccessedAt`. Stable (ties keep prior relative order). Default ascending; `--desc` reverses (e.g. `--by last-activity --desc` = most-recently-active first). Reply mirrors `group reorder`
  - `nex layout cycle|select <name>`
  - `nex open [--here] <path-or-url>` — generic opener that routes **in the CLI**, reusing existing wire commands. A **URL or hostname** argument opens a web pane (same `web-open` path as `nex web open`, prints `open ok: <uuid>`): a real `scheme://` URL, a `host:port`, `localhost[:port]`, an IPv4 literal, or a bare dotted hostname whose final label is a recognised TLD (`webOpenCommonTLDs`) — so `nex open google.com`, `nex open https://example.com`, `nex open localhost:3000` Just Work. Otherwise it routes a **local file** by (lowercased) extension: markdown extensions (`md`, `markdown`, `mdown`, `mkd`, `mkdn`, `mdwn`, `markdn`) send the `open` command → markdown pane; web extensions (`html`, `htm`, `pdf`, `svg`, `png`, `jpg`, `jpeg`, `gif`, `webp`) build a `file://` URL and send `web-open` → web pane; any other extension is a usage error pointing at `nex md` / `nex web open`. The file-vs-host split is decided by `webTargetForOpenArg(_:)` — the mirror of `localFileURL(forWebArg:)`: explicit paths (`/`, `./`, `../`, `~`) and existing local files always stay local (so `./google.com` is a file, and a bare word like `README` / an unrecognised or file-type TLD like `notes.txt` / `foo.museum` falls through to the file router — use `nex web open` for those). `--here` (reuse the calling pane) applies to the markdown route only — it's ignored with a stderr note for URLs and web files, which always open a new pane. The routing tables live in `markdownOpenExtensions` / `webOpenExtensions` / `webOpenCommonTLDs` in `Tools/nex-cli/nex.swift`.
  - `nex md [--here] <filepath>` — dedicated markdown command; always opens (or `--here`-reuses) a markdown preview pane regardless of extension. Same `open` wire command as `nex open`'s markdown route; the escape hatch for forcing a markdown pane on a non-`.md` file.
  - `nex diff [<path>]` — opens a diff pane for the CLI's current working directory (or scoped to `<path>`). The diff pane refreshes on focus and via the header refresh button.
  - `nex web open|navigate|tab-new <url>` resolve **local file paths** to `file://` URLs CLI-side (issue #177): the `localFileURL(forWebArg:)` helper in `Tools/nex-cli/nex.swift` converts an argument that is path-shaped (`/`, `./`, `../`, `~` prefix), or a **bare name matching a regular file _with an extension_** in the cwd, into a percent-encoded `file://` URL (expanding `~`, resolving against cwd). Bare hostnames (`example.com`), single-label hosts that collide with a cwd directory (`app`, `web`, `api`), extensionless names, and real URLs pass through untouched — the existence branch deliberately excludes directories and extensionless names so it can't hijack a dev hostname (review of #177); `./name` forces a local path. Server-side, `WebPaneCoordinator.load(_:into:)` loads `file://` URLs via `loadFileURL(_:allowingReadAccessTo:)` (parent dir) so a local HTML file's sibling assets resolve; remote URLs use a normal `URLRequest` load. The app is not sandboxed (`Nex.entitlements` → `app-sandbox` is `false`), so the directory read grant works without a security-scoped bookmark.
  - `nex doctor [--json]` — IPC health check. Runs seven named checks (`transport`, `socket`/`resolve`, `ping`, `process`, `version`, `hooks`, `codex-hooks`) and prints pass/fail/warn with concrete repair tips. Use when CLI commands stop reaching the app: `ping` exercises the same dispatch path as a real CLI command, `process` distinguishes "Nex isn't running" from "Nex is wedged", and `version` flags CLI/app drift. `hooks` is a local check of the user-level Claude Code config (`~/.claude/settings.json` + `settings.local.json`, `$HOME`-resolved; project scopes not checked; skipped when `~/.claude` doesn't exist): it verifies every nex hook from `install-hooks.sh` is wired, that `disableAllHooks` isn't set, and that the `SessionStart` entry's matcher (if any) covers `startup`/`resume`/`clear`/`compact` using Claude Code's documented matcher semantics (`*`/empty = all, `|`/`,`-separated exact list, else regex — `DoctorReport.matcherCovers`). A stale pre-v0.19 `"startup"` matcher means resumed sessions (`claude --continue`/`--resume`) never bind their session id (issue #181). Hook drift is WARN, not FAIL (IPC is healthy; agent tracking degrades) — doctor exits non-zero only on FAIL. The expected hook set lives in `DoctorReport.expectedHooks`; `install-hooks.sh` writes `SessionStart` matcher-less (fires for all sources) and `merge_hooks.py` migrates stale matcher groups and dedupes nex-managed commands by flag-less base command (absolute-path and `--agent`-flagged variants included) on re-run. `codex-hooks` mirrors the same states for `~/.codex/hooks.json` (expected set in `DoctorReport.expectedCodexHooks`, adjacent to `expectedHooks`): skipped when `~/.codex` is absent, WARN-only on drift; inline `[hooks]` tables in codex's `config.toml` are not parsed (can false-warn) and hook *trust* isn't inspectable, so the repair text always includes the `/hooks` re-trust step.
- **CLI transport selection**: `NEX_SOCKET` env var selects transport. Absent = Unix socket (`/tmp/nex.sock`). `tcp:<host>:<port>` = TCP (e.g., `NEX_SOCKET=tcp:host.docker.internal:19400`).
- **Categorised transport errors**: `Tools/nex-cli/nex.swift` classifies socket failures into a `TransportFailure` enum (`unixSocketMissing`, `unixConnectRefused`, `tcpConnectFailed`, `emptyReply`, etc.) and prints an `Error: …\nRepair: …` pair at each call site via `printTransportFailure`. Fire-and-forget commands (Claude Code hooks etc.) preserve exit code 0 but now print a `Warning: …` stderr line — set `NEX_SILENT=1` to suppress entirely. `nex event …` (the hook entrypoint) auto-suppresses the warning to avoid spamming user terminals on every Stop/Notification fire; set `NEX_VERBOSE_HOOKS=1` to surface them. `lastTransportFailure` is reset at the start of every send call so chained CLI commands (e.g. `nex doctor` running ping then ps) can't carry stale diagnostics between calls.
- `StatusBarController` — menu bar icon + popover showing running/waiting agents across workspaces.
- `NotificationService` — desktop notifications with "Open"/"Dismiss" actions.

### Keybindings
- **Config file**: `~/.config/nex/config` — Ghostty-style `key = value` syntax. General settings: `focus-follows-mouse`, `focus-follows-mouse-delay`, `theme`, `tcp-port`. Keybindings: `keybind = super+d=split_right`. Workspace profiles: `profile = <name>:<KEY>=<value>` (one var per line; repeated lines merge by name, later wins). Parsed by `ConfigParser`, loaded by `KeybindingService`.
- **Data model** (`KeyBinding.swift`): `KeyTrigger` (keyCode + modifiers), `NexAction` (51 bindable actions, including the web-pane verbs and the default-unbound `open_diff` / `toggle_sync_input` / `web_zoom_in` / `web_zoom_out` / `web_zoom_reset`), `KeyBindingMap` (trigger → action dictionary with sorted lookups).
- **Two dispatch layers**: SwiftUI `Commands` (`NexCommands`) handles menu bar shortcuts; `PaneShortcutMonitor` (NSEvent local monitor) handles pane-context shortcuts. Both read from `AppReducer.State.keybindings`.
- **Settings UI** (`KeybindingsSettingsView`): table grouped by category with key recorder sheet, per-action reset, and reset-all. Changes are persisted to the config file.
- **Conditional shortcuts**: `toggle_markdown_edit` only fires for markdown panes, `close_search` only when search is active, `close_pane` deletes workspace when it's the last pane.

### Dependencies (TCA DependencyKey pattern)
All services are registered as TCA dependencies: `surfaceManager`, `persistenceService`, `gitService`, `socketServer`, `notificationService`, `statusBarController`, `ghosttyConfig`, `workspaceProfiles`. Tests use `testValue` (e.g., in-memory DB, no-op managers).

### Workspace profiles
- Named env-var sets in the config file (`profile = work:CLAUDE_CONFIG_DIR=~/.claude-accounts/work`), assigned per workspace (`WorkspaceFeature.State.profileName`, persisted in `WorkspaceRecord`). `WorkspaceProfilesClient` re-reads the config per call — definitions stay fresh without a watcher. Env is injected at surface spawn (`SurfaceView.init` → `ghostty_surface_config_s.env_vars`) plus a `NEX_PROFILE=<name>` marker; `NEX_PANE_ID`/`PATH` are reserved (built-ins win). Spawn-time only: live PTYs keep their birth env. Every spawn path threads env — reducer effects, the socket group-create path, the restart-restore path (so `claude --resume` lands in a PTY already on the right account), and the `SurfaceContainerView.makeNSView` lazy-create fallback (which races the reducer effect; both must inject or profiles get flaky). Multi-account Claude Code is the flagship use case: one workspace per `CLAUDE_CONFIG_DIR`.
- **Built-in `default` baseline**: `WorkspaceProfilesClient.defaultProfileName`. An unassigned workspace (stored `profileName == nil`) resolves the `default` profile at spawn, so every pane gets `NEX_PROFILE` (=`default` unless assigned) plus any vars the user defines under `default`. `normalizedAssignment` maps "default"/empty → nil, so `default`, `--clear`, and fresh workspaces are one state. The Settings tab pins `default` first (name locked, undeletable, virtual until it has vars — only then written to the config).
- **Definition management**: hand-edit the config file, or Settings → Profiles (`ProfilesSettingsView`, storeless — the config file is the source of truth; loads with `parseProfiles(expandTilde: false)` so `~` values round-trip unexpanded, writes through `ConfigParser.writeProfiles`, which replaces all `profile` lines while preserving every other config line).

## Key Conventions

- **Swift 6 concurrency**: use `nonisolated(unsafe)` for mutable state protected by `NSLock`. Use `@preconcurrency` for Obj-C protocol conformances.
- **XcodeGen**: `project.yml` is the source of truth. Never edit `Nex.xcodeproj` directly — regenerate with `xcodegen generate --spec project.yml`.
- **libghostty**: prebuilt static library at `lib/libghostty.a`, header at `ghostty/include/ghostty.h`. Bridging header at `Nex/Ghostty/Ghostty-Bridging-Header.h`.
- **Test guard**: `NexApp.isTestMode` prevents ghostty initialization during test runs.
- **TCA testing**: `TestStore` closure receives pre-action state; mutate to expected post-state. Use `@Dependency(\.uuid)` with `.constant()` for predictable IDs. Test suites need `@MainActor`.

## Release Process

1. Bump version in `Nex/Info.plist` (both `CFBundleShortVersionString` and `CFBundleVersion`)
2. Commit: `chore: bump version to X.Y.Z`
3. Push to `main`
4. Create and push tag: `git tag vX.Y.Z && git push origin vX.Y.Z`
5. GitHub Actions handles archive, sign, notarize, DMG, and appcast update
6. Update release notes via `gh release edit` with a proper changelog

Do NOT run `make release`, `make archive`, or `make dmg` locally.
